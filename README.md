# افق دانش ثریا (Odsco) — سامانه یکپارچه شرکتی

نسخه **۲.۰** — سایت معرفی + پیام‌رسان داخلی + مدیریت پروژه + حضور و غیاب + خودکارسازی + پنل کارفرما.

---

## ۱) نصب

### الف) پیش‌نیازها
- PHP **8.1+** با افزونه‌های `pdo_mysql`, `mbstring`, `session`, `gd` (اختیاری، برای بهینه‌سازی تصویر)
- MySQL **5.7+** یا MariaDB **10.3+**

### ب) مراحل
1. فایل‌ها را در هاست قرار دهید.
2. در مرورگر باز کنید: **`https://yoursite.com/install/`**
3. اطلاعات دیتابیس را وارد کنید. نصب‌کننده:
   - اتصال را آزمایش می‌کند
   - **۳۴ جدول** و ۳۶ ایندکس را می‌سازد
   - داده‌های قدیمی `data/*.json` را به دیتابیس **مهاجرت** می‌کند
   - فایل `includes/config.local.php` را می‌نویسد (این فایل در گیت نیست، چون رمز دیتابیس دارد)

### ج) نصب دستی (بدون ویزارد)
```bash
mysql -u USER -p DBNAME < database/schema.mysql.sql
```
سپس `includes/config.local.php` را بسازید:
```php
<?php
return [
    'driver'   => 'mysql',
    'host'     => 'localhost',
    'port'     => 3306,
    'database' => 'odsco',
    'username' => 'odsco_user',
    'password' => '••••••••',
    'charset'  => 'utf8mb4',
    'prefix'   => '',
    'debug'    => false,
];
```

### د) زمان‌بندی (Cron)
روزی یک‌بار برای اجرای خودکارسازی‌ها:
```
0 7 * * * php /path/to/site/tools/cron.php --key=YOUR_CRON_KEY
```
یا اگر کرون خط فرمان ندارید، از طریق URL:
```
https://yoursite.com/tools/cron.php?key=YOUR_CRON_KEY
```
کلید را در **پنل مدیریت → تنظیمات → زمان‌بندی** بسازید و عوض کنید.

## ۳) پیام‌رسان داخلی

**ذخیره‌سازی محوری روی دستگاه کاربر:** هر پیام هم در دیتابیس (برای تحویل) و هم در
**IndexedDB** روی گوشی/کامپیوتر کاربر ذخیره می‌شود. نتیجه:

- تاریخچه و فایل‌ها **آفلاین** در دسترس‌اند
- سرور را می‌توان پاک کرد بدون اینکه کاربر چیزی از دست بدهد
- مدیر می‌تواند در تنظیمات، نگهداری سمت سرور را محدود کند (مثلاً ۳۰ روز)

**امکانات:** گفتگوی خصوصی، گروه، «پیام‌های ذخیره‌شده»، واکنش (❤️👍😂😮😢🙏)،
پاسخ، فوروارد، ویرایش، پین، حذف برای من / برای همه، جستجو، بی‌صدا کردن،
وضعیت خوانده‌شده (✓/✓✓)، «در حال نوشتن…»، آنلاین/آخرین بازدید،
مدیریت دستگاه‌ها، اعلان‌ها، آپلود تصویر/فایل/ویدیو/صوت.

**API:** همه درخواست‌ها از `messenger/api.php` با پارامتر `action` عبور می‌کنند.

## ۴) مدیریت پروژه

- تعریف پروژه با **کارفرما**، **مدیر پروژه**، تاریخ شروع/پایان، درصد پیشرفت
- **انتخاب اعضا** با نقش هر عضو در پروژه
- **میز کار** (`admin/workspace.php`): برد کانبان (در انتظار / در حال انجام / بررسی / انجام‌شده)،
  درصد پیشرفت هر تسک، نظرات و گزارش کار
- پیشرفت کلی پروژه به‌صورت خودکار از میانگین تسک‌ها بازمحاسبه می‌شود
- **گزارش پیشرفت** در چهار سطح: اطلاع / پیشرفت / هشدار / بحرانی
  با قابلیت «فقط داخلی»، «فقط کارفرما» یا «هر دو»

## ۵) حضور و غیاب

دو روش همزمان:

1. **اسکن QR** — مدیر QR می‌سازد، کارمند اسکن می‌کند (ورود/خروج خودکار تشخیص داده می‌شود).
   QR قابل قفل‌کردن روی IP شبکه شرکت است.
2. **درخواست دستی** — کارمند درخواست ثبت می‌فرستد، مدیر تایید یا رد می‌کند.

گزارش‌ها: برگه روز، برگه ماه، گزارش ماهانه هر کارمند (ساعات کار، تاخیر، غیبت، مرخصی، مأموریت)،
ثبت خودکار غیبت روز قبل از طریق کرون.

تنظیمات: ساعت شروع/پایان کار، آستانه تاخیر، اعتبار QR، روزهای تعطیل هفتگی.

## ۶) خودکارسازی (Automation)

قواعد «اگر این رویداد رخ داد و این شرایط برقرار بود، این کار را بکن».

**رویدادها:**
| رویداد | چه زمانی |
|---|---|
| `project.update.created` | ثبت گزارش پیشرفت پروژه |
| `task.overdue` | تسک از سررسید گذشته |
| `task.due_soon` | سررسید تسک نزدیک است |
| `attendance.absent` | کارمند غایب است |
| `attendance.late` | کارمند تاخیر داشته |
| `client.message` | پیام جدید از فرم تماس سایت |
| `project.deadline_soon` | مهلت پروژه نزدیک است |
| `cron.daily` | اجرای روزانه |

**گیرندگان اعلان:** مدیران، کارکنان، اعضای پروژه، **کارفرمایان پروژه**، مسئول تسک،
مدیران ارشد، یا لیست صریح شناسه‌ها.

**متغیرهای قابل استفاده در متن:** `{project}` `{title}` `{progress}` `{task}` `{assignee}`
`{due_date}` `{user}` `{name}` `{subject}` `{level}`

**ارسال اطلاعیه دستی** (`admin/broadcast.php`): یک پیام، همزمان به سه کانال —
اعلان درون‌سیستمی، پیام خصوصی در پیام‌رسان، و ثبت در تایم‌لاین پروژه.

## ۷) پنل کارفرما

ورود مستقل با حساب نقش `client`. کارفرما فقط:
- پروژه‌های شرکت خودش را می‌بیند
- فقط پروژه‌هایی که «قابل نمایش برای کارفرما» علامت خورده‌اند
- فقط گزارش‌هایی که سطح دیدشان `client` یا `both` است

امکانات: داشبورد، تایم‌لاین پیشرفت، تصاویر پروژه، تیم اجرایی،
گزارش‌های قابل دانلود (CSV) و چاپ، اعلان‌ها.

## ۸) ساختار کد

```
includes/
  db.php          لایه PDO (MySQL/SQLite) — تنها دروازه اجرای کوئری
  schema.php      منبع حقیقت همه جدول‌ها + تولید SQL برای MySQL
  repo.php        همه ریپازیتوری‌ها (Users, Projects, Tasks, Media, ...)
  messenger.php   منطق پیام‌رسان
  attendance.php  منطق حضور و غیاب
  automation.php  موتور قواعد + ProjectAlert
  migrate.php     مهاجرت JSON → دیتابیس
  jalali.php      تبدیل تاریخ شمسی ↔ میلادی
  helpers.php     ابزار مشترک، امنیت، آپلود
  auth.php        احراز هویت سه‌بخشی (ادمین / پیام‌رسان / کارفرما)
  config.php      بوت‌استرپ + لایه سازگاری read_json/write_json

messenger/assets/
  local-store.js  فروشگاه IndexedDB (آفلاین)
  messenger.js    کلاینت API + رندر
  chat.js         کنترل‌کننده گفتگو

tools/
  run-tests.sh    اجرای همه مراحل تست (۱ تا ۶)
  smoke-test.php  ۱۷۹ assertion روی مسیرهای واقعی کد
  check-api.php   بررسی سازگاری همه فراخوانی‌ها با API واقعی
  render-test.sh  رندر واقعی ۴۵ صفحه با نشست واقعی
  api-test.php    فراخوانی واقعی ۳۱ اکشن از ۳۲ اکشن messenger/api.php
  cron.php        ورودی زمان‌بندی روزانه
```

### سازگاری با کد قدیمی
`read_json()` و `write_json()` همچنان کار می‌کنند، اما منبعشان دیتابیس است.
اگر دیتابیس نصب نباشد، به همان فایل‌های `data/*.json` برمی‌گردند.
این یعنی صفحات عمومی سایت بدون تغییر کار می‌کنند.

## ۹) تست

```bash
bash tools/run-tests.sh
```

اسکریپت شش مرحله را به‌ترتیب اجرا می‌کند:

| # | مرحله | خروجی مورد انتظار |
|---|---|---|
| ۱ | بررسی نحوی همه فایل‌های PHP (`php -l`) | `✅ همه فایل‌ها بدون خطای نحوی` |
| ۲ | نصب اسکیمای دیتابیس تست + مهاجرت داده‌های واقعی | `۳۴ جدول / ۳۴۱ رکورد` |
| ۳ | تست یکپارچه | `نتیجه: 179 موفق / 0 ناموفق` |
| ۴ | سازگاری فراخوانی‌ها با API واقعی | `۲,۰۳۲ فراخوانی بررسی شد` |
| ۵ | رندر واقعی صفحه‌ها | `نتیجه رندر: 45 موفق / 0 ناموفق` |
| ۶ | اکشن‌های API پیام‌رسان | `نتیجه API: 65 موفق / 0 ناموفق` |

> اکشن `upload` از `messenger/api.php` چون به `$_FILES` نیاز دارد در مرحله ۶ صدا زده
> نمی‌شود؛ منطق آپلود آن (`Messenger::uploadFile`) در مرحله ۳ پوشش داده شده است.

در پایان باید `🎉 همه تست‌ها موفق` چاپ شود.
فایل موقت `includes/config.local.php` که برای تست ساخته می‌شود در پایان پاک می‌شود.

اجرای جداگانه هر بخش:
```bash
php tools/smoke-test.php     # لایه داده و سرویس‌ها
php tools/check-api.php      # سازگاری فراخوانی‌ها
bash tools/render-test.sh    # رندر صفحه‌ها
php tools/api-test.php       # اکشن‌های API پیام‌رسان
```

> **توجه:** تست‌ها روی **SQLite** اجرا می‌شوند چون در محیط توسعه سرور MySQL در دسترس نیست.
> لایه `Db` هر دو گویش را پشتیبانی می‌کند، اما مسیر MySQL باید روی هاست واقعی آزموده شود.
